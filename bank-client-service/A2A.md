# A2A in bank-client-service

This service is an **A2A client**: it delegates to two **A2A servers**, the Python `informations-agent` and `actions-agent`. This page covers how that works end to end: the protocol, the wire format, where each piece lives in the code, and how failures and confirmations are handled.

## 1. A2A in five concepts

[A2A](https://a2a-protocol.org) (Agent2Agent) is an open protocol (JSON over HTTP) for one agent to delegate work to another, whatever framework each one is built with. Here, a TypeScript agent built with the Vercel AI SDK talks to Python agents built with LangChain.

| Concept | What it is | Here |
|---|---|---|
| **Agent Card** | JSON document at `/.well-known/agent-card.json`: the agent's name, skills, endpoint URL, protocol binding and version | Fetched once per agent by `ClientFactory.createFromUrl()` |
| **Message** | One turn: `role`, `parts` (`text`, `data` = JSON, files), free `metadata`, optional `contextId` / `taskId` | Our request: a text part (+ a data part for decisions), `metadata.client_id` |
| **Task** | The unit of work created by the remote agent: `id`, `contextId`, `status.state`, `status.message`, `artifacts` | What `SendMessage` returns |
| **Context** (`contextId`) | Groups the tasks of one conversation, so the remote agent can remember earlier turns | One per conversation per remote agent, generated by us |
| **Artifact** | The result of a completed task (`parts`) | The remote agent's answer text |

Task states we handle:

| State | Meaning | What we do |
|---|---|---|
| `completed` | Done; result in the artifacts | Return the answer to the model |
| `input-required` | **Paused**: the agent needs more input on the same task | Actions agent only: show Approve/Reject to the client |
| `rejected` | Refused before any work (e.g. missing `client_id`) | Tool error to the model |
| `failed` | Error during the work (LLM down, timeout) | Tool error to the model |
| `canceled` | Canceled with `CancelTask` | Tool error to the model (not used by us) |

## 2. Transport and versions

- Binding: **JSON-RPC 2.0** over HTTP `POST` to the URL in the Agent Card (`supportedInterfaces[0].url`, here the agent's root `/`). Method: `SendMessage`.
- Protocol version: **1.0**, sent as the `A2A-Version: 1.0` HTTP header. The JS SDK reads the version from the Agent Card and adds the header itself. The Python servers refuse requests without it, since they would be treated as protocol 0.3.
- Blocking calls: the request returns once the task is `completed`, `failed`, `rejected` or `input-required`. No streaming (SSE) and no push notifications: the remote agents answer within seconds, and their cards advertise neither.
- SDK: `@a2a-js/sdk` ≥ 1.3, client side only (`@a2a-js/sdk/client`).


## 4. Asking for information

```
client: "Quel est mon solde ?"
  → model calls ask_informations_agent({ request: "Balance of all accounts" })
  → tool context (set by code): { clientId: "c_001", contextId: <conversation.remoteContextIds.informations> }
  → A2A SendMessage to :8001
  ← Task completed, artifact "Checking account (**** 0185): 1842.50 EUR. …"
  → model rephrases it in French for the client
```

What goes over the wire (JSON-RPC body, as serialized by the SDK):

```json
{
  "jsonrpc": "2.0", "id": 1, "method": "SendMessage",
  "params": { "message": {
    "messageId": "b0c7…", "role": "ROLE_USER",
    "contextId": "5e2a…",
    "parts": [{ "text": "Balance of all accounts" }],
    "metadata": { "client_id": "c_001" }
  }}
}
```

and back:

```json
{ "jsonrpc": "2.0", "id": 1, "result": { "task": {
  "id": "77f1…", "contextId": "5e2a…",
  "status": { "state": "TASK_STATE_COMPLETED" },
  "artifacts": [{ "name": "answer", "parts": [{ "text": "Checking account (**** 0185): 1842.50 EUR. Savings account (**** 0142): 12500.00 EUR." }] }]
}}}
```

- **`metadata.client_id`** is the only thing that tells the remote agent whose data to read. It comes from `res.locals.clientId` (identity middleware) → `Conversation.clientId` → call options → tool context. The model never sees or writes it.
- **`contextId`** is generated when the conversation is created (`randomUUID()`) and reused for every call to that agent. So "and the savings account?" works on the remote side too.
- **No `taskId`**: every request is a new task.

## 5. Performing an operation: the confirmation flow

The actions agent pauses every write (card block, transfer) in **`input-required`** until it receives a structured decision on the same task. We make sure that decision comes from the client's click, never from the model.

```
 Client (UI)             bank-client-service                             actions-agent (A2A)
     │ "block my card 4821"     │                                               │
     │ ───────────────────────▶ │ model → ask_actions_agent("Block card 4821")  │
     │                          │ ── SendMessage {text, client_id, contextId} ─▶│ model calls block_card
     │                          │                                               │ → paused before it runs
     │                          │ ◀── Task input-required ───────────────────── │
     │                          │      status.message: text summary + data      │
     │                          │ tool output: confirmation_required            │
     │                          │   (taskId kept in code, hidden from the model)│
     │                          │ conversation.pendingConfirmation = {taskId,   │
     │                          │                                     summary}  │
     │ ◀─ status: "confirmation_required", confirmation.summary, answer         │
     │ [Approve] [Reject]       │                                               │
     │                          │                                               │
     │ click Approve ─────────▶ │ POST { conversationId,                        │
     │                          │        confirmation: { decision: "approve" } }│
     │                          │ ── SendMessage {taskId, contextId, client_id, │
     │                          │      parts: [data {decision}, text comment?]}▶│ resumed → block_card runs
     │                          │ ◀── Task completed, artifact "Card blocked" ─ │
     │                          │ model gets "[Bank app] The client clicked …   │
     │                          │   Actions agent result (completed): …"        │
     │ ◀─ "Votre carte est bloquée."                                            │
```

The reply that resumes the paused task:

```json
{ "jsonrpc": "2.0", "id": 2, "method": "SendMessage", "params": { "message": {
  "messageId": "…", "role": "ROLE_USER",
  "taskId": "77f1…", "contextId": "9c3d…",
  "parts": [ { "data": { "decision": "reject" } }, { "text": "Actually only 50" } ],
  "metadata": { "client_id": "c_001" }
}}}
```

Rules, and why:

| Rule | Why |
|---|---|
| The decision is a `data` part, sent by `BankAgent.runConfirmation()` from the request's `confirmation` field | The actions agent never treats text as consent, and the model has no way to produce a decision. |
| The summary shown to the client comes from the actions agent (built from its database) | The client approves what will really run, not a paraphrase. |
| The remote `taskId` is removed from the model's view of the tool result (`toModelOutput`) | The model doesn't need it, and can't misuse or invent it. |
| A new client message drops the pending confirmation | The actions agent rejects a paused task as "superseded" when a new task starts in the same context, so an old confirmation can never be approved by accident. Clicking a stale button then gets a `409`. |
| The client's comment is forwarded as a `text` part | The actions agent passes it to its model with the rejection, e.g. "Actually only 50" → it offers to prepare 50 EUR instead. |
| If the decision call fails with a network error, the confirmation is kept | Retrying is safe: the actions agent refuses a decision for a task that is no longer paused. |
| If the actions agent restarted (`TaskNotFoundError`), the confirmation is dropped and the client is told nothing changed | Paused tasks are kept in memory: an approval after a restart can never run anything. |

## 6. Failures

| What happens | Where | Result for the client |
|---|---|---|
| Remote agent down, network error, Agent Card unreachable | `callRemote()` in tools/remoteAgents.ts | Tool error "The … agent is unavailable right now." → the model apologizes and suggests the app or a phone line |
| Remote task `failed` / `rejected` | `describeFailure()` | Tool error with the remote status message → same |
| Remote call slower than 100 s | `A2ARemoteAgent.timeoutMs` | Aborted → tool error |
| Agent Card fetch failed earlier | `A2ARemoteAgent.getClient()` | Not cached: the next call fetches it again, so starting the Python agents after this service works |

## 7. Trying it by hand

```bash
# Agent Cards
curl -s localhost:8001/.well-known/agent-card.json | jq .
curl -s localhost:8002/.well-known/agent-card.json | jq .

# Through the front agent
curl -s localhost:3000/api/v1/chat -H 'content-type: application/json' \
  -d '{"message":"Block my card ending in 4821, I lost it"}' | jq .
# → status "confirmation_required"; then, with the returned conversationId:
curl -s localhost:3000/api/v1/chat -H 'content-type: application/json' \
  -d '{"conversationId":"<id>","confirmation":{"decision":"approve"}}' | jq .
```

To call the Python agents directly with raw JSON-RPC, see `informations-agent/README.md` and `actions-agent/README.md`.

## 8. Not done yet

- **Authentication between agents** (`TODO(auth)`): the Python agents trust `metadata.client_id`. In production, this service would authenticate to them (e.g. an OAuth2 client-credentials token, declared in their Agent Cards' `securitySchemes`), and the client id would come from a verified user token, ideally signed so the remote agent can check it.
- **Streaming**: `sendMessageStream()` + `capabilities.streaming` would let the UI show progress during long delegations.
- **Persistence**: conversations, A2A tasks (Python `InMemoryTaskStore`) and paused runs (LangGraph `InMemorySaver`) are all in memory.
